# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Emberhold: a top-down browser game. Three teams (Amber, Azure, Jade) of five heroes (Anvil, Dart, Patch, Cog, Forge) each guard an Ember. AI enemies attack every Ember each night; rival heroes can attack at any time; the last Ember standing wins. Bots play every hero no human picks. `README.md` has the player-facing rules and controls.

## Commands

```bash
npm install
npm start          # http://localhost:3000, this computer only (PORT env overrides the port)
npm run lan        # same, bound to 0.0.0.0: for a LAN, or as the start command on an internet host
npm start -- --lag=150 --jitter=40   # simulate a slow line (round-trip ms, extra ms each way)
npm test           # node --test "test/*.test.js"
npm run balance    # 60 bot-only matches from a random seed, every hero checked against bounds (under a minute)
node test/balance.test.js 100 4242   # the same for any match count and first seed; a seed repeats a run exactly
npm run balance:endless   # 12 bot-only endless matches from a random seed (about half a minute); `node test/balance.test.js endless 30 7` for any count and seed
node test/balance.test.js 30 1001 --eclipse=volatile   # any balance run with every Eclipse night under one Eclipse (blood_moon, iron_tide, ash_storm, volatile)
node --test test/bots.test.js                                     # one file
node --test --test-name-pattern="Anvil bot raids" test/bots.test.js   # one test
```

There is no build step, linter or bundler. The only dependency is `ws`. The code uses `import.meta.main` and `import.meta.dirname`, so it needs a recent Node (developed on v26). `.claude/launch.json` defines the preview servers `emberhold` and `emberhold-slow` (simulated lag), both on port 3000.

## Committing

More than one Claude session may be working in this folder at once. Stage only the files you changed, by name (`git add path/to/file`). Never `git add -A`, `git add .` or `git commit -a`: they sweep up another session's unfinished edits. A changed file you did not touch belongs to someone else: leave it alone and say so.

## Architecture

One code path: the server is always authoritative, solo play included.

- `public/sim.js` holds every rule. It is pure and headless: `createGame(seed)` returns the state, `step(state, inputs, dt)` advances it. It lives in `public/` because both sides import it: the server runs it, and the browser imports its constants and `canBuild` (for the build ghost) from the same file.
- `public/bots.js` exports `botInput(state, heroIndex, spend)`. It returns the same input object a human client sends, and keeps no memory between calls. `spend` (default true) lets the bot use its team's Scrap; the server lets bots build on every team, a human's included, but passes `reserve` (`RESERVE`, 35) for a team with a human on it, so a bot there never takes the pool below 35 Scrap; and the touch client passes false when it borrows `botInput` for auto-aim.
- `server.js` exports `startServer()`. It serves `public/` and runs one match at 60 Hz, sending the whole state as JSON at 30 Hz. The match is created when the first human joins and discarded `grace` seconds (default 60) after the last one leaves; a human who leaves hands their hero to a bot.
- `public/client.js` only sends input and draws. It blends snapshots with `public/interp.js` and predicts its own hero's steps, shots and builds locally.
- `public/net.js` is the client netcode that must hold up over the internet, kept free of the DOM so Node can test it: `createTimeline` (which moment to draw), `createPredictor` (own-hero movement), `createGunPredictor` (own shots), `createBuildPredictor` (own builds) and `createFxPredictor` (the bursts of own abilities).

### Things that span files

- **Inputs.** Humans and bots both produce `{mx, my, aim, fire, use, q, r, build, remove}`; a human's may also carry `ping` (see Pings). `step` takes an array (or object) indexed by hero slot. Held fields are state; `q`, `r`, `build`, `remove` and `ping` are one-shot. The server rebuilds every client input from scratch in `readInput` before the sim sees it. A human client does not send `fire`: it sends `shoot`, one order for each volley it draws, and `tick` in `server.js` holds `fire` down for that hero until the sim's own cooldown lets the volley go, so client and server always count the same shots. At most `VOLLEYS` (3) orders wait at once, and they lapse while the hero is down or stunned. Bots still return `fire`.
- **Hero slots.** A hero's index is `team * TEAM_SIZE + k`, where `k` is its position in `HERO_IDS` (`anvil, dart, patch, cog, forge`); `teamOf(slot)` gives the team. A Shield Generator's field (and a Forge's own) raises a nearby hero's `shieldMax` each tick. Tests, the server's seats and the client all rely on this.
- **State is plain JSON.** The snapshot is `JSON.stringify(state)`, so nothing non-serialisable may go in it. Derived data (cell lookup, wall grid, one flow field per Ember) lives in a `WeakMap` in `sim.js` keyed by the state and rebuilt when `s.sv` changes (the flow fields are kept when the change left the wall grid as it was, as Spikes do). Anything that adds or removes a structure must bump `s.sv`; use `addStruct` and the existing removal path rather than touching `s.structs` directly.
- **Determinism.** The sim uses its own seeded RNG; the same seed and inputs must give the same state (a test checks it). Do not use `Math.random` or the clock in `sim.js` or `bots.js`.
- **Hostility.** Every hero, shot and structure carries a `team`; AI enemies are hostile to all three. There is no friendly fire within a team, and a team walks and shoots through its own Walls.
- **Netcode contract.** Each `state` message carries `n` (the server tick, which is the clock the client's timeline runs on, not arrival time), `acks` (per hero slot, the last input `seq` the server has heard; a snapshot only ever follows a tick, so the held keys, Q and R of an acked input have been acted on) and `done` (per hero slot, the last input whose build and remove orders have been tried: orders queue at one a tick, so `doneTo` in `server.js` holds this back while one waits). The client compares the server's position for its hero with where it had predicted itself when input `acks[slot]` went out, so lag is not mistaken for error. It walks its prediction with the sim's own `moveHero`, so Walls stop it exactly as they stop the server.
- **Predicted shots and builds.** Only the picture is predicted, never an outcome. Pulling the trigger draws stand-in shots at once at the gun's own rate, stopped by the sim's own `shotHit`; when the server's copies arrive a round trip later they are hidden rather than drawn twice (`gun.hides`), and a shot nobody predicted is drawn as usual. Each stand-in volley sends the server a `shoot` order and the server fires one volley an order, so a stand-in always exists before its copy can arrive and the two are paired by count. A hidden copy stays hidden for a second after the server drops it, because the drawn world runs behind the newest snapshot and is still showing it. An ordered structure is drawn at once and its Scrap counted as spent (`mayBuild`, `place`); it is kept until the drawn world shows the server's own, and taken away, with its Scrap, as soon as the input that ordered it is `done` with no such structure standing (a refusal shows a round trip after the click; the one-second wait is only for a dead line). Pressing Q or R (`cast` in `client.js`) plays its sound, draws its burst and starts the HUD's cooldown at once; the stand-in cooldown ends when that input is acknowledged, whatever the server decided, and the server's copy of the burst is hidden when it arrives (the effect of a hero's Q or R carries that hero's slot as `owner`, so a teammate's burst is never taken for ours; no other effect has an `owner`). Whether a Q or R may be shown at all is the sim's own `canCast`; Dart's Dash also moves the predicted hero by the sim's own `dash`, before the input's position is recorded, so the server's answer agrees with it. Damage, kills, healing and Scrap still change only when the server says so.
- **Bandwidth.** Snapshots stay whole-state JSON; one deflate stream per connection, run by `server.js` itself and read by `createUnpacker` in `net.js`, does the delta work (about 700 KB/s raw, about 40 KB/s on the wire, in a bot-only match). Every server message goes through it as newline-separated JSON. It is not left to the WebSocket's `perMessageDeflate`, because Render's proxy strips that. Adding fields that change every tick for every entity costs more than their size suggests.
- **Connections.** A client makes up a `key` and sends it with `join`; showing it again takes its seat back from a connection that died unnoticed. The server pings every `beat` ms and drops silent connections, refuses connections past `maxClients`, and cuts off one that floods. Against DNS rebinding, both the page and the WebSocket are refused unless the Host header is an IP address, `localhost` or the computer's own name (`ownHost`); `anyHost` (set on Render, or by `--any-host`) lifts that for a public host reached by its domain.
- **Look and sound.** `public/art.js` paints everything in art pixels (`PX` = 0.5 art pixels per world unit) on a small canvas the page scales up by a whole number; sprites are drawn once in code, outlined and cached. `public/sound.js` synthesises every effect. There are no image or audio files. `client.js` plays sounds from what changed between snapshots (`hear`), using the ids on shots and effects. The same differences set off `boom`: sparks and a camera jolt when an Ember falls, a Colossus dies or slams, a hero goes down or Aegis goes up (the `BOOM` table). When the player's own Ember loses health, `hear` sets `alarmUntil`: for a second and a half its bar in the HUD is outlined (`.ember.hit`), and if the Ember is off screen `art.pointer` draws an arrow towards it at the edge of the view, inside the HUD's panels. Sparks, shake and the alarm live only in the client, never in the state, and the camera stays still when "Screen shake: off" is chosen under Settings (saved in localStorage; off by default where the system asks for reduced motion). The match's colour mood is `s.mood`, fixed at `createGame` from the seed (`s.seed` itself is the RNG state and changes constantly); the HUD's panel colours follow it through CSS variables. The HUD font is Silkscreen from Google Fonts, falling back to monospace offline.
- **Touch.** `public/touch.js` turns a thumb drag into the same move input the keyboard produces, so nothing in the sim or server knows which a player uses; phone and PC are one client, not two versions. On touch, `sendInput` in `client.js` takes aim and fire from `botInput` (the bots' own target choice) and scavenges automatically near a wreck, leaving the player to move, build and use Q and R. Building on touch has two styles chosen under Settings (saved in localStorage): drag to place, or Auto-build, which places `nextPiece` from `bots.js` (the bot Cog's blueprint). Touch-only HUD pieces carry the `touchonly` class and show when `body.touch` is set.
- **Arena and power-ups.** The playable ground is the circle `ARENA` in `sim.js` (centred on the three Embers); `inArena`, `keepIn` and the `LAND` cell mask keep heroes, enemies, shots, wrecks, building and pathing inside it, while `WORLD` is still the rectangle the grid and ground image cover. Killed AI enemies may drop `s.pickups` (`POWERUPS`: rush, fury, mend) using the seeded RNG; heroes carry `rush` and `fury` timers.
- **Upgrades.** A `build` order of the same type on the team's own finished structure upgrades it (`canBuild` returns null for it, `tryBuild` does it): the structure gets `tier: 2`, half as much more `max`, full health, and `TIER2` (1.5) times its Turret damage, Spikes damage or Shield Generator barrier, for its cost again, once. Structures that were never upgraded carry no `tier` field, which keeps it out of the snapshot. No structure is added or removed, so `s.sv` is not bumped. The client sends an upgrade only on a press, never while dragging a line (`order` in `client.js`); its stand-in carries `tier: 2`, and `createBuildPredictor` matches on tier as well as cell, team and type, so the order is paid when the upgraded structure shows up and not by the one it was ordered on. `art.tier2` draws the gold corners. The bot blueprint (`BLUEPRINTS` in `bots.js`) ends with every piece again marked `up: true`, guns first, so `nextPiece` moves on to upgrades once the base stands.
- **Eclipses.** `ECLIPSES` in `sim.js` (`blood_moon`, `iron_tide`, `ash_storm`, `volatile`). `startNight` picks one with the seeded RNG on every third night (and every second from night 12 in endless mode), never the one in `s.lastEclipse`; `s.eclipse` holds its key until `startDay` clears it. A match with `s.onlyEclipse` set has that one on every Eclipse night; `createGame` does not put the field there and the server never sets it, only the balance harness's `--eclipse=<id>` does. Each rule reads its number through `eclipsed(s, key)`, which gives 1 (or the `none` passed) on any other night: enemy speed and aggro range, the Breaker count in `pack`, AI damage to structures (the three places an AI enemy hurts one: a strike, a slam, a Spitter's shot), and Turret range. What an Eclipse does that is not a multiplier is registered in `ECLIPSE_HOOKS` by the moment it happens (`spawn`, `death`), and `spawnEnemy` and `hurtEnemy` call whatever tonight's has: an Ash Storm's `spawn` gives the enemy a `shield`, which `hurtEnemy` takes from first and deletes when it is gone; Volatile's `death` is `burst`, which hurts heroes and structures in reach in full and other AI enemies at `toEnemies` (0.45) of that, and no Ember: deaths still chain, but only through AI enemies already hurt, so a wave does not clear itself. A death inside a chain pays its plain bounty: `hurtEnemy` adds the Eclipse's extra Scrap only while `chain` is empty. That keeps the extra for Turret and Spikes kills, which carry `owner: -1` just as a chain death does, so `owner` cannot tell them apart. A chain is a queue (`chain`), drained inside the first burst's call and empty again when it returns, so its length costs no stack. The shield and the blast grow with `level(s)` (`ashShield`, `volatileBlast`: `shieldGrow` and `blastGrow` of the table's number more for each level after the first), so the table holds first-night values, 26 and 22, which come to 34 and 24.2 on night 3. The shield grows 15% a level because it is measured against AI enemy health, which grows 25%; the blast grows 5% because it is measured against hero health, which does not grow. Bots back out of the bursts they cannot afford (the `BOMB_HP` constants in `bots.js`): an AI enemy is about to burst at 30 health or 16% of its own, whichever is more; a bot at full health shrugs off a small burst, a medic at a dying teammate and a Fortified Anvil stay while it leaves them health to spare, and a Forge on a repair run keeps a wider berth. The client names the Eclipse in the dusk banner and in the HUD's phase line.
- **The Core.** `CORE_DEF` in `sim.js`. On every other day from the second (`s.wave` odd: days 2, 4, 6), `step` puts `s.core = { x, y, team, prog }` at the arena's centre `spawnDelay` seconds into the day (`s.coreSpawned` keeps it to one a day); `startNight` removes it. `coreContestants(s)` is the one test of who is in the ring (the living heroes of each standing team, and `lead`, the team with more there than any other): `updateCore` decides by it and the client colours the ring by it. A team alone fills the Core, after running a rival's progress down; with rivals in the ring too, the team with the most heroes still has it, at the slower `contestedRate` and `contestedRundown`; a tie for the most holds it where it is, and an empty ring drains it at `decayRate`. The days without one are left for raiding. Taking it pays Scrap, mends the Ember, and gives the team's living heroes Ultimate charge and Rush, with a `capture` effect (`payCore`). At dusk `startNight` pays `dusk` (half) of that, without the Rush, to a team that leads the ring with its own progress at least half way there, and nothing to a team that leads over a rival's progress. Bots never collect it: they turn for home about ten seconds before dusk, so it is a rule for players. The ring is 135 across its radius so that a hero with a gun has room to move inside it. The bot Dart and Anvil go to it in place of raiding, and the Patch follows once a teammate is there. The Anvil walks into the ring and holds it whoever comes (`hold`); the Dart and the Patch fight from there as they do anywhere, which means backing off to their guns' range, and so out of the ring, when a rival comes near. Two rules count heads with `coreContestants`: a Patch whose teammates in the ring do not lead without it, but would tie or lead with it, goes in and stands just inside the rim, at 0.85 of the radius (`tip`), provided it has 55% of its health, or 40% once the progress in the Core is its team's own (`TIP_HP`, `TIP_STAY`: the gap keeps it from stepping out and back in as its health crosses one line); and an Anvil gives the ring up when two or more of one rival team hold it and no teammate is within 2.5 radii (`lost`), as it does with its shield broken or under half health (`roam`). It then fights them from its gun's range as a Dart does; `lost` once set a stopping distance too, which the firing band already supplied. Two flags in `botInput` send a bot straight to its goal past the firing band: `transit` (hurt and going home or to its medic's side, a medic going to a patient, a Forge going to a repair or home when outmatched), which passes power-ups by, and `hold` (the Anvil, or a tipping Patch, in the ring), which still steps out for a power-up within 80 of the ring (`PICK_NEAR_RING`). Until the Anvil held the ring, two teams of bots were never in it together and neither rule ever fired. With the ring at 135 they share it about 11% of the time a Core stands (12 matches from seed 1001; it was 5% at 110), nearly always one Anvil against another, a tie that holds the Core where it is; the Patch tips some of those. The guard posts (`post`) are turned to face mid-map for each team, as the wrecks are: before that Amber's Dart started 200 units nearer the Core than Jade's and Amber took 43% of them.
- **Pings.** A player calls the bots on their team with Z, X or C: `ping` in the input, one of `PINGS` (`defend`, `core`, `raid`). `readInput` drops any other word, `updateHero` puts `T.ping = { kind, ttl: PING_TTL }` (8 seconds) on the caller's team even while the caller is down, and `updateStructs` counts it down and deletes it, so a team nobody has called to carries no `ping` in the snapshot. Bots never send one. In `botInput` a `defend` call counts as the Ember being under attack for every bot, with the night's leash so that a bot far from home comes back rather than fight where it stands; `core` and `raid` send every roaming bot, the Cog and the Forge included, to the Core (if one stands) or to `raidTarget`, and the Cog builds nothing meanwhile. A bot that is hurt, exposed or defending is not roaming and finishes that first. The client shows a call as a badge from the snapshot, so a teammate's shows as one's own does. There is no button for it on touch.
- **Triage.** Patch's passive: `heroSpeed(h, s, mx, my)` is `HEROES.patch.triage.speed` (1.2) times faster when `triage(s, h, mx, my)` says the Patch is walking towards an injured teammate: a living one under half health (`below`), anywhere on the map, with the move within about 45 degrees of the line to them (`cone`, a cosine), so circling a fight does not count and a teammate who is down is no patient. `heroSpeed(h)` alone still gives the plain speed. `updateHero` passes the match and the move, and so does the client's `follow`, with the hero placed where it predicts itself, so both sides walk at the same speed; `triage` may therefore read nothing but the state and the move.
- **Options and accessibility.** All of it lives in the client and in `localStorage`, none in the state. `prefs` in `client.js` (`emberhold-prefs`) holds `contrast`, `autofire` and `rings` beside `build` and `shake`; the Settings sheet has a button for each, a Master volume slider (`sound.volume`, kept under `emberhold-volume` and multiplied into every sound) and Quick help. High contrast is `setPalette` in `art.js`: it swaps `TEAMS[k].color` for a colourblind-safe set (Jade turns pink), empties the sprite cache, and turns on `pip`, the team's shape (`PIPS`: triangle, square, disc) that the hero, Ember and structure painters each draw; the HUD and the hero select screen are rebuilt to take the colours and lead team names with the shape. It changes `sim.js`'s own `TEAMS` table, which no rule reads. Auto-fire (T; F was taken by scavenging) holds the trigger down. The build ghost's rings are the build range, each rival Ember's no-build radius, and the reach of the piece. `badge` in `client.js` puts a short badge under the banner for what is otherwise only heard ("Ember under attack", "Core active", "Eclipse dusk"), and for a call to the bots. `showHelp` (the ? key) writes the Quick help sheet from `HEROES`, `TIER2` and `ECLIPSES`, so it cannot fall behind them.
- **Endless mode.** `s.endless` (false by default) is set by the server when the match is created, from the `endless: true` of the `join` that started it (the checkbox on the hero select screen), and kept across Play again. In it `step` ends the match only when no Ember is left, the winner being the last to fall, and difficulty climbs at `ENDLESS_PACE` (half) of the usual step per night through `level(s)`, which enemy health, damage and pack size all read. Bot-only endless matches last about 22 minutes, to night 17, and the last Ember stands alone for only about a minute of that. A player whose Ember is lost (`h.out`) can send the camera round the Embers and heroes still in the match with Q and E (`spectate` in `client.js`, which sets `watch`); WASD flies it freely again.
- **Static files.** The server only serves a literal file name directly inside `public/` ending in `.html`, `.js` or `.css`. A new asset type or a subfolder needs that check in `server.js` changed.

## Tests

Node's built-in runner, no test dependencies. `test/sim.test.js` covers rules, `test/bots.test.js` covers bot decisions plus seeded full bot-only matches checked for sane state, `test/server.test.js` starts a real server on a random port with WebSocket clients (`newGame` is injectable so a test can start from a prepared match).

`test/balance.test.js` is the balance harness. It plays bot-only matches on worker threads and fails when a hero's damage per minute or deaths per match stray too far from the average of the five, when a team wins far from a third of the matches, or when matches run too short, too long or never end. Under `npm test` it plays 12 fixed-seed matches against wide bounds (`QUICK`) and 10 endless ones (`ENDLESS`: every match ends, average nights and minutes, how long the last Ember stands alone, with a per-hero table for the team that was last standing); given a match count on the command line it plays that many normal matches against tight bounds (`FULL`) and prints a per-hero table. `--eclipse=<id>` on any of those runs puts every Eclipse night under one Eclipse and says so in the report's first line; the bounds are still those of the game as played, so read a failure there as a measurement. Both reports also print the Cores each team took and the largest snapshot (`maxSnapBytes`: the state as JSON, looked at once a second; about 57 KB at the peak of an average match and 62 KB at most, an Ash Storm night no larger than any other). The endless matches are most of the harness's 50 seconds: each costs about three normal ones.

To judge a change to one bot rule, a symmetric run says little, since all three teams get it. Keep a copy of the old `bots.js`, give one team the new `botInput` and the other two the old, and play every seed three times with the new seat rotating; compare that team's wins with a third.

Bot tests mostly build a state by hand (place heroes, set `g.wave`, clear `g.wrecks`) and assert on a single `botInput` result, using the `quiet()` and `heading()` helpers in `test/bots.test.js`.

Nothing automated runs the browser client. `test/client.test.js` only checks its files against each other, such as a build button for every structure. `test/art.test.js` is a smoke test: it loads every browser module but `client.js` in Node, and calls every painter in `art.js` against a stand-in canvas, so a module that no longer loads, a painter that throws, or a structure, enemy or hero with no painter fails `npm test`. It cannot say whether anything looks right: check drawing and HUD changes by playing in a browser.

The `architectural-review` skill builds one markdown file of chosen source files plus a written summary, for an outside reviewer. It is not in this repository: it lives in the user's own skills folder (`~/.claude/skills/architectural-review/`, with its script and that script's tests) so that every project can use it. The bundles it writes in the project root (`emberhold_codebase_context.md` by default) are not committed (they show as untracked).

## Balance changes

Hero, structure and enemy numbers are the tables at the top of `sim.js` (`HEROES`, `STRUCTS`, `ENEMIES`). Judge a balance or bot-behaviour change with the harness: run `node test/balance.test.js 60 1001` before and after (the same first seed plays the same matches) and compare the tables, then `npm run balance` for a fresh random sample. Change a bound in `FULL` or `QUICK` only on purpose, and say why in the commit.

Damage per minute settles to within a point or two of the average by 12 matches. Deaths need 60 to settle to about a tenth, and a team's win count swings by several even then.

A rule that takes the first of several equal candidates takes it by hero slot, and so by team. `weakestHostile` in `bots.js` did, between two unhurt rivals: Jade's heroes come last in the list, were shot last, and Jade took 95 of 215 Cores to Azure's 50 (60 matches from seed 1001). It takes the nearer now, and every group of pieces in the bot blueprint goes up nearest mid-map first for the same reason. Break such ties by something on the map; the harness's `Cores taken` line is the quickest sign of a bias like it.

## Known limits

- One match per server process, open to anyone who has the address (no rooms, no password).
- Your own movement, shots and builds are drawn at once, but only drawn: hits land when the server hears the shot, so damage lags by the connection's delay and there is no lag compensation for aiming. A predicted shot can pass something the server's shot hits, or stop where the server's does not. Of the abilities, only the feedback (sound, burst, cooldown) and Dart's Dash are predicted: what a Q or R does to anyone still waits for the server. Cog's Sentry and removing a structure are not predicted at all.
- Shot prediction gives up on an answer after one second, so on a line slower than that a shot may be drawn twice. A player's gun fires only while their page is drawing, since each volley is ordered by the frame that draws it: a hidden tab does not shoot, and below about 16 frames a second Dart's Overdrive fires slower than its rate. Builds and abilities go by the acknowledged input instead, and wait a second only when no answer comes at all.
- No automated test covers the browser's use of `net.js`; `test/net.test.js` covers the module itself, the two predictors included.
